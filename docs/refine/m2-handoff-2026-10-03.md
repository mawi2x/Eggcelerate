## Delivered behavior

Monitoring hydration depends on modes and incubators. Alerts, hatch history, and
settings now have their own loading/error/retry states. Their initial failures do
not replace healthy monitoring. Critical initial failures retain the farm-load
error and retry view; cached monitoring remains visible during refresh failures.

The notification bell and feed expose alert fetch status. Missing server alerts
are labeled unavailable rather than shown as an empty successful feed. Hatch
History exposes a retry state and hides totals/records until history is available;
environmental charts remain usable. Settings exposes a retry state and prevents
editing fallback preferences while real settings are unavailable. Header account
identity falls back to the signed-in user during settings loading.

Background failures retain loaded values, with a stale label and last-update
stamp for alerts, history, and settings. Ordinary successful background updates
do not replace the screen with a loading placeholder. Sensor history and Trends
keep available readings with their existing retry feedback; Trends explicitly
labels cached readings as potentially out of date after an update failure.

The earlier [fetch-notification policy](m2-fetch-notifications-2026-10-03.md)
remains: one local grouped episode, bounded toasts, recovery/read/dismiss behavior,
and no persistence into durable device alerts.

## Refresh policy

| Data / action | Policy |
| --- | --- |
| Incubator status and mounted readings | Every 15 seconds while authenticated and visible; immediate refresh on tab return |
| Farm alerts | Every 15 seconds while authenticated and visible; immediate refresh on tab return |
| Hatch history | Every 60 seconds while authenticated and visible; immediate refresh on tab return and entering Trends |
| Trends entry during an existing history fetch | Join the in-flight fetch instead of cancelling/restarting it |
| Modes and settings | Existing cache/mutation behavior; feature Retry for settings failures |
| Pending turn command | Existing two-second cadence, now gated by authentication as well as command availability |
| Background tab | Periodic refresh pauses; returning refreshes the monitored/shared queries |
| Live-refresh environment flag | `VITE_LIVE_REFRESH_ENABLED=false` disables periodic status/readings/alerts/history polling; mount, tab-return, route-activation, and explicit Retry remain available |
| Logout / session expiry | Disable queries and polling, clear private cache and local notifications; a late query response cannot restore cleared private data |

API session hydration now accepts an abort signal. Expiry/unmount cancels that
check, and a response that ignores cancellation is still prevented from restoring
identity or CSRF state. Mock logout/account changes clear the provided query cache;
standalone mock-auth consumers remain supported without a query client.

## Screen and app recovery

Screen error boundaries preserve the navigation shell and reset when the selected
screen/chamber changes. The application boundary also catches provider/app rendering
failures. Both offer Try again and a dashboard escape; ordinary render failures
remount through explicit retry. Lazy routes recreate their React.lazy instance on
retry instead of reusing a rejected promise.

Browsers can cache a failed module download. For recognized chunk/module/CSS-load
errors, Try again explicitly reloads the page, with that behavior explained in the
fallback. A Firefox aborted-module check reproduced this case and confirmed the
retry downloads and opens the screen. Page reload is recovery for that exceptional
failure; ordinary data updates continue without reloading.

Lazy-route declarations live in their own module so App exports remain compatible
with Vite Fast Refresh.
